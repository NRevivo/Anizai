## §1 — Scope

Add the two streaming/dynamic UI features deferred from earlier sprints:

1. **Suggested actions** — 3 contextual follow-up suggestions per forecast.
2. **Chain-of-thought events** — `agentEvents` stream during **main forecast**
   processing, displayed by the frontend reasoning panel **while the session is
   running only** (display rule is a frontend-contract item; storage is permanent
   — see §3).

**Out of scope (decided 2026-07-04):** follow-up runs do NOT emit events. A
follow-up is answered in ~2–4s through 3 internal steps — a reasoning panel adds
nothing; the frontend shows a simple "thinking" indicator derived from the user
message's `status` (`sent` = agent working, `answered` = done; zero hub work).
This also removes the multi-stream sequence-collision problem and keeps the ≤7s
follow-up budget untouched.

**Blockers:** none — Sprint 24 closed 2026-07-04. **Precondition:** T25.0 — the
KG-B-19 **triage fork** must be resolved before any feature commit. "Resolved"
means one of the two forks is taken and recorded: (2) the empty-`invoke({})` test
defect is fixed and KG-B-19 closed as a test defect — **no dependency change** — or
(3) the failure reproduces with a non-empty input and the version audit runs. It is
NOT an "env fix" precondition; that framing (the pre-2026-07-14 wording) is retired.
**Next action:** T25.0.

## §3 — Confirmed design decisions (revised 2026-07-04, Advisor↔Ron; pre-implementation review 2026-07-15)

- Suggested actions generated by an extra GPT-4o-mini call after `synthesize`, to
  keep main synthesis lean.
- Schema: `{id, label, prompt}`. Frontend uses one default icon for all (V1 "simpler
  dynamic" agreement).
- **Event emission is NON-BLOCKING (decided 2026-07-04).** Nodes never wait on a
  Firestore round-trip for an event: `emit_event`/`complete_event` enqueue to an
  in-process ordered queue and return immediately; a dedicated background writer
  thread drains the queue in FIFO order (order preserved so the panel never shows
  a step completing before it starts). Rationale: ~20 blocking writes per forecast
  add wall-clock and are fragile under network jitter; cosmetic UI events must
  never slow the forecast. "Fire-and-forget" (below) covers *error* behavior;
  this decision covers *blocking* behavior — both are required.
  - **Run-end drain:** before `write_to_firestore` flips the session to `done`,
    the queue is flushed (bounded wait) so the final events aren't lost. Same
    drain on graceful worker shutdown.
- agentEvents writes are fire-and-forget: write failures are logged and swallowed,
  never failing the agent.
- **Every event carries `runId`; `sequence` and `runId` live in the EMITTER, not on
  state (pre-handoff findings #2).** LangGraph nodes return partial dicts — an
  in-place `state["sequence"] += 1` inside a helper does not propagate, and making
  every node return the counter is brittle boilerplate that recreates the
  shared-field-merge risk. Instead: `agent/events.py` holds a **per-`runId` guarded
  registry** of emitter contexts (each a thread-safe `sequence` counter + the minted
  `runId`); `init_run` registers one keyed by `runId`, resolved per-emit by the
  explicit `run_id` a node reads from state (§3-F, refined 2026-07-15 — NOT
  thread-local), and disposed at run END (`dispose_run`, process_query finally —
  NOT idle-pruned, which would drop an active concurrent run; corrected
  2026-07-15) (see §3 review correction F — a single
  global counter would silently interleave two runs' events once
  `AGENT_MAX_CONCURRENT_SESSIONS` > 1). `ForecastState` gains **exactly one**
  new field, `run_id: str`, written **once** by `claim_session` (single writer — no
  merge semantics). `sequence` orders events *within* a run; `runId` namespaces
  runs. `runId` exists for the planned "re-run forecast" button — a second run on
  the same session must not bleed events into the first run's panel.
  - **`currentRunId` on the session doc (findings #5):** `claim_session` already
    updates the session doc twice (`claimed`, then `running`); it additionally
    writes `currentRunId: <run_id>` **on the `running` transition** — zero extra
    writes. Frontend rule: render only the event group whose
    `runId == session.currentRunId`. **This is a HARD partner blocker (§3
    correction G), not polish** — the deployed panel filters strictly on this field
    read from Firestore; without it, nothing renders.
    - **Ordering is contractual:** `currentRunId` must land on the session doc
      **BEFORE** `init_run` and before the first event is emitted. Otherwise a
      listener can observe `agentEvents` docs whose `runId` has no matching
      `session.currentRunId` yet, and Rule B ("render only
      `runId == currentRunId`") silently drops them for the width of that window.
- **Run context initializes only AFTER `claim_session` resolves the real session id;
  NO event may be emitted before that point (findings #3).** On resume-on-clarify
  runs the initial `state["session_id"]` is the fresh forecastQueries doc UUID, and
  `claim_session` overwrites it with the actual session id from the claimed doc.
  An event emitted earlier would land under `sessions/{fresh-uuid}/agentEvents` —
  a subcollection under a non-existent parent, created silently by Firestore with
  no error. Gate 2 must assert the resume case writes events under the ORIGINAL
  session id.
- **Failure path (findings #4):** `fail_event`'s owner is `process_query`'s
  exception branch (alongside `_mark_failed`, the code that already owns run
  death), so an aborted run never leaves its last event dangling `running`;
  `events.drain(timeout)` is called in a `finally` there (belt-and-suspenders under
  the pre-`done` drain), and `worker.main()` drains after unsubscribing the watches
  and before the health-server shutdown. All drains are non-raising, consistent
  with fire-and-forget. **The `awaiting_clarification` terminus is covered by the
  same `finally` drain:** a clarification run ends without reaching
  `write_to_firestore`, so the pre-`done` drain never fires — the `finally` flushes
  its events. Display-wise nothing extra is needed: Rule A already hides the panel
  on `awaiting_clarification`, and the resume run mints a fresh `runId` +
  overwrites `currentRunId`, so the panel shows only the new run's events.
- **Events are stored permanently but DISPLAYED only while the session is running
  (decided 2026-07-04).** Storage-vs-display are separate decisions: records stay
  (survive mid-run page refresh — the panel's critical moment; per-stage
  timestamps beside the session for initial-test diagnostics and the 26.3 latency
  analysis; deleting 20 docs would itself cost 20 writes). Display rule (frontend
  contract): the reasoning panel renders only while status is
  `queued/claimed/running`; once `done`, events are never rendered again,
  including on re-opening an old session. No event compaction/deletion job is
  needed for V1 (25.8 stays deferred).
- **Latency NFR context:** the main-forecast NFR was relaxed to ≤60s p95
  (KG-B-5, 2026-07-04). This does NOT license blocking event writes — the
  non-blocking decision stands on robustness grounds. The follow-up ≤7s budget
  is unaffected by this sprint (follow-ups emit nothing).

### Pre-implementation review corrections (2026-07-15, Advisor↔Ron, verified vs. the deployed frontend)

The pre-implementation review — run against the actual repo, the partner's deployed
frontend, and the rewritten `frontend-integration` skill — answered the open enum
question, fixed the event-status vocabulary, and closed three "works-now,
breaks-silently-later" gaps. These are **authoritative and override** any earlier
wording in this file that conflicts.

- **A. Event `type` is an OPEN-VOCABULARY string = the emitting node's own name** —
  NOT a fixed enum. Each node emits `type` equal to its node name. The deployed
  frontend reads `type` as a plain string (no enum lock), and the Sprint-26 latency
  analysis (26.3) reads these stage names — mapping nodes onto a fixed enum (the
  rejected option b) would lie to both. New nodes emit new `type` strings, no
  contract change needed. (The closed enum in the *old* `frontend-integration` was a
  stale design doc, now fixed.)

- **B. Event `status` vocabulary = `pending` | `running` | `done` | `failed`** —
  matching the partner's already-implemented `AgentEvent.status` union exactly. The
  hub emits a start event with status `running` and completes it to `done` (or
  `failed` on the failure path). We match their four values, NOT the reverse;
  wherever earlier drafts said `in_progress`/`complete`, read `running`/`done`.
  (`pending` is in the union for the frontend's own use; the hub's start event goes
  straight to `running`.)

- **C. Event doc field set the emitter MUST write** (every field the panel reads):
  `eventId`, `sessionId`, `runId`, `sequence`, `timestamp`, `type`, `title`,
  `description`, `status`, `durationMs`, `payload`. Two specifics:
  - `durationMs` is derived from the start→complete delta (null until complete) —
    easy to miss; the completing call computes and writes it.
  - **Do NOT write `parentMessageId`** — a dead field from the cancelled
    follow-up-events design; the partner is removing it on their side too.

- **D. Gap 1 — the pre-`done` drain has an explicit OWNER and a pinned ORDER.**
  Owner: `write_to_firestore` (T25.4). The final write step runs in this exact order:
  1. write all forecast outputs (evidence / predictionSeries / sentimentTimeSeries /
     sessionResults incl. `suggestedActions`);
  2. complete the last event (status `done`);
  3. `events.drain(timeout)` — flush the queue;
  4. flip session `status = done`;
  5. flip the `forecastQueries` doc `status = done`.
  Rationale: if `done` is flipped before the drain, the last events land **after** the
  panel has stopped rendering (frontend Rule A hides the panel on `done`); with no
  drain at all, the last event dangles `running` forever. (Gate 2 / T25.10 asserts
  the drain completes before the `done` flip.)

- **E. Gap 2 — there are ELEVEN main-graph nodes (not five).** T25.6 wires emission
  into all of them; the two **conditional-branch** nodes are named explicitly because
  they only run when their branch is taken (easiest to forget) and are exactly the
  non-standard paths where the user most needs the panel to explain what happened:
  1. `claim_session` †  2. `query_understand`  3. `write_clarification` (branch)
  4. `build_embedding`  5. `vault_query`  6. `sufficiency_check`
  7. `trigger_reactive_ingestion` (branch)  8. `rate_evidence`  9. `synthesize`
  10. `generate_suggested_actions`  11. `write_to_firestore`.
  - † `claim_session` is the emitter **bootstrap**: it mints `run_id`, writes
    `currentRunId`, calls `init_run`, and **then emits a single one-shot `done`
    bootstrap event** (title "Analyzing your question…") before returning `run_id`.
    It is a lone `done` event, **NOT** a start/complete pair — the claim is
    instantaneous, so a pair would write a meaningless `durationMs`; a one-shot `done`
    (durationMs `null` or `0`) gives the panel its first line at first paint (an empty
    panel under status `running` reads as *stuck*) without distorting durations
    (decision 2026-07-15, Flag #1). The other **ten** each emit the
    start(`running`) + complete(`done`) pair; the bootstrap event is the panel's first
    line, followed by `query_understand`'s.

- **F. Gap 3 — the run registry is a PER-`runId` GUARDED MAP, not a single global.**
  It works today (one forecast at a time), but `AGENT_MAX_CONCURRENT_SESSIONS` exists
  as a forward-flag; the moment it exceeds 1, a single global counter would interleave
  two runs' events into one sequence, silently. Requirement:
  - `init_run(session_id, run_id)` registers a `RunContext` (session_id + a
    lock-guarded `sequence` counter) in a module-level `{run_id: RunContext}` map.
    **Run resolution is by EXPLICIT `run_id` (refined 2026-07-15, NOT thread-local):**
    nodes pass `state["run_id"]` (the single-writer field `claim_session` mints) to
    `emit_event`/`complete_event`, because LangGraph may run nodes on pool threads
    where a thread-local set in `claim_session` would not propagate. Explicit run_id
    is robust to LangGraph's threading and still per-run/guarded;
  - each event captures its `runId` + `sequence` **at enqueue time** (counter
    incremented under the run's lock), so the value on the queued event is fixed
    regardless of any other run;
  - the background writer drains the single shared FIFO; `drain(timeout)` blocks until
    the queue is empty (bounded, non-raising); the run is disposed from the map at
    run END (`dispose_run`, process_query's finally, after the drain) — NOT pruned by
    "no in-flight events", which would drop an active run that is momentarily idle
    between nodes under concurrency (corrected 2026-07-15 while writing Gate 1 tests).

- **G. `currentRunId` is a HARD partner dependency, not polish.** The deployed
  reasoning panel filters strictly on `runId == session.currentRunId`, read directly
  from Firestore. `claim_session` writing `currentRunId` on the `running` transition —
  before the first event — is what makes the panel show anything at all. Confirmed
  with the partner; it is the blocker on their side.

- **Testing infra (state the need before each gate, per `code-review` skill B1):**
  - **T25.0 (KG-B-19 triage) runs DRY — no emulator, no Docker.** That specific test
    builds an in-memory toy `StateGraph` and never touches Firestore. Run with a
    non-empty input (`graph.invoke({"session_id": "x"})`); green → test defect (fix
    input, close KG-B-19, change **nothing** in `requirements*.{txt,lock}`).
  - **Gate 2** runs against mocked Firestore — no containers.
  - **Gate 3 (T25.11)** needs the **Firestore emulator** up; bringing it up is what
    makes KG-B-18 execute and fail, which the **T25.14** skip-guard covers. State the
    infra need so Ron brings the base infra up; the sprint brings up the specific
    containers and tears down what it brought up at sprint end.
